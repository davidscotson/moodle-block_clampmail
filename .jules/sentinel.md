## 2026-02-15 - [IDOR in Alternate Email Actions]
**Vulnerability:** The `block_clampmail\alternate::get_one($id)` method previously retrieved records based purely on the record's primary ID without scoping it to the course ID. Similarly, `confirmed` deleted records solely by ID. This allowed any user with appropriate permissions in any course to view, modify, or delete alternate email configurations in other courses via tampered request parameters (IDOR).
**Learning:** Functions that query or mutate records by database ID must always explicitly validate that the record belongs to the user or context associated with the active session. Relying on permission checks at the controller level without enforcing strict resource ownership scopes on helper queries leaves the system vulnerable to direct object reference exploitation.
**Prevention:** Always require contextual scoping parameters (e.g., `courseid`, `userid`) alongside the primary entity `id` in database queries and delete operations, and enforce MUST_EXIST or strict checks to validate resource context ownership before completing the action.
