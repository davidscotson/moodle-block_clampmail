## 2025-05-14 - Scoping Database Operations in Moodle Blocks
**Vulnerability:** Insecure Direct Object Reference (IDOR) and Cross-Site Request Forgery (CSRF) in record management.
**Learning:** In Moodle, simply checking permissions with `require_capability` is insufficient if subsequent database operations (`get_record`, `delete_records`) use only a primary ID. Attackers can manipulate IDs to access or delete records from other courses or users. Additionally, state-changing actions via direct links (like "reset" or "confirm delete") must be protected with `sesskey`.
**Prevention:** Always scope database lookups and deletions using a context ID (e.g., `courseid`) and, where applicable, the `userid`. Use the `MUST_EXIST` flag in `$DB->get_record` to ensure the application fails securely if scoping fails. For state-changing actions, use `require_sesskey()` and include `sesskey()` in generated URLs. For dynamic method calls, use an explicit whitelist of allowed methods instead of `method_exists`.
